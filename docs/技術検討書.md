# 軽量地震速報アプリ 技術検討書 (v2)

作成日: 2026-08-13
目的: 常時表示型の地震速報アプリの技術方針を固め、開発用Claudeへの入力とする。

---

## 1. 要件(確定)

| 項目 | 内容 |
|---|---|
| 表示端末 | Raspberry Pi 4 + フルHDモニター、ブラウザで常時表示(キオスク) |
| サーバー | N150 CPUのミニPC。Dockerイメージでhttp公開、リバースプロキシでhttps終端 |
| 中心機能 | **強震モニタ(リアルタイム震度マップ)は必須**。これ単体でも成立させる。ただし見た目は改善したい |
| 通知 | EEW・地震速報の受信をトリガーに**音 + 画面明滅**。モニターを注視し続けなくても気づける状態にする |
| EEW範囲 | **端末ごとに「予報まで/警報のみ」を切り替え**できるようにする |
| 津波 | 津波予報の表示が望ましい(利用地: 宮崎県延岡市 = 日向灘沿岸) |
| 費用 | 無償のデータソースのみ(DM-D.S.Sは使わない) |

### 前提の更新(v1からの変更)

強震モニタが常時表示必須になったため、v1の「平常時は通信ほぼゼロ」は成立しない。**平常時から毎秒(または2秒毎)の画像取得が発生する**。ただしN150サーバーが1回だけ取得し、家庭内の全端末へ配る構成にすれば、外部への負荷はクライアント数に関係なく一定にできる。

## 2. 【最重要】強震モニタの利用規約 — 構成を縛る制約

**原文通読済み**(2026-08-13時点、 https://www.kyoshin.bosai.go.jp/ja/about_kmoni/ )。要点:

**(1) 複製・再配布の禁止**: 強震モニタコンテンツの複製は私的使用・引用等著作権法上認められた行為を除き禁止。複製したコンテンツの転載・改変・送信・再配布は固くお断り、と明記。
- 2023年の規約変更時にJQuake等で騒動になった実績があり、形骸化した条文ではない(経緯: https://akagire.hatenablog.com/entry/2023/07/05/094927 )。
- **本システムへの影響**: N150サーバーがkmoni画像を取得してクライアントへ中継する行為は「送信・再配布」に該当しうるため、利用範囲を**私的使用に収める**ことが成立条件。
  1. リバースプロキシに入場制限を付ける。**nginxのBasic認証で確定**(発注者決定)。利用範囲は「自宅LAN+発注者本人の会社PC」に確定
  2. 画面にNIED(防災科研)のクレジットを表示する
  3. 不特定多数向けサービス化・配信への転用はしない

**(2)「強震モニタ利用にあたってのお願い」による制約(原文で確認)**:
- 「**個別観測点での色の変化の検知や、色から観測値を抽出する**など、防災科研が意図していない形での利用」が名指しされており、「このような防災科研の意図しない形で**処理した情報を公開もしくは配信することはお控えください**」と明記。→ **旧Phase 4(画像ピクセル→震度値復元)はこれに該当するため計画から除外**(§6)。延岡付近の震度数値は、地震後に気象庁発表の実測震度(P2P 551)で代替する。
- 「強震モニタで表示している**緊急地震速報の震源情報等に依拠した即時的な情報配信**を行うことはお控えください」と明記。→ kmoni EEW JSONの利用は**自宅内の私的表示に限定**し、第三者への配信・公開・通知サービス化には使わない。
- 平常時も生活振動・ノイズで色が変化するため、個別観測点の色変化への注目は不適切、との注意あり(誤検知設計の参考)。

**(3) 気象業務法**: kmoniのEEW震源情報を抽出して独自に地震動を予測し公開することは予報業務にあたり気象業務法の制限を受ける、と明記。表示は配信された値・画像のままに留める(独自の到達予測・震度予測計算をしない)。

**(4) 免責**: コンテンツ・配信形態は予告なく変更/削除されうる。過度のアクセス集中時は配信停止・遅延がありうる。→ 劣化モード(§4)は必須。

**副産物 — kmoni公式の表示条件(通知閾値設計の参考)**:
- 予報の表示条件: 気象庁の2点以上の地震計で観測+震源深さ150km以浅+M3.5以上または最大予測震度3以上
- 警報の発表条件: 最大予測震度5弱以上、または長周期地震動階級3以上

### その他ソースの規約(確認済みの範囲)

- **P2P地震情報**: 無料・登録不要・商用可( https://www.p2pquake.net/develop/ )。ただし**2026年6月からWebSocket接続はIPあたり2本**( https://p2pquake.hatenablog.jp/ )。サーバー集約構成なら1本で済み好都合。
- **「地震津波火山ネットワークセンターのデータ公開に関する考え方」通読済み**( https://www.mowlas.bosai.go.jp/policy/guideline/ 、平成29年制定・令和2年改定)。要点: データは原則として防災科研に帰属し**再配布・販売・改ざん禁止**(kmoni規約(1)と同趣旨)、公開データは**予告なく提供中止・改訂されうる**(劣化モードの根拠)、利用者の行為・損害について免責。本書の方針(私的使用限定・劣化モード必須)と整合し、追加の制約なし。

## 3. データソース(無償構成・確定案)

| 情報 | ソース | 方式 |
|---|---|---|
| リアルタイム震度マップ | kmoni 画像 `.../RealTimeImg/jma_s/{日付}/{時刻}.jma_s.gif` | サーバーが毎秒〜2秒毎に取得しクライアントへ配布 |
| EEW(予報・警報両方) | kmoni EEW JSON `.../webservice/hypo/eew/{時刻}.json` — `alertflg`が「予報」「警報」を持つ | サーバーが毎秒ポーリング。**無償で予報レベルまで取れる唯一の現実解** |
| EEW(警報)の冗長系 | P2P地震情報 WebSocket code=556(警報)・554(発表検出) | サーバーが常時接続1本 |
| 地震情報(震度速報・震源) | P2P地震情報 code=551 | 同上 |
| **津波予報** | P2P地震情報 code=552 | 同上。宮崎県沿岸の予報区を強調表示 |
| P/S波到達円・予想震度(地震時) | kmoni `PSWaveImg/eew/...gif`・`EstShindoImg/eew/...gif` | 地震時のみ取得 |
| 時刻基準 | kmoni `webservice/server/pros/latest.json` | 起動時+定期でオフセット補正 |

EEW範囲の端末別切替は、サーバーは常に予報+警報を配信し、**クライアント側の設定(localStorage等)で「予報を通知するか」をフィルタ**する実装が最も単純。なおkmoni EEW JSONに現れる予報は「深さ150km以浅+M3.5以上または予測震度3以上」を満たしたもののみ(§2副産物参照)であり、微小地震まで鳴り続ける心配はない。kmoni EEW JSONの利用は私的表示に限定する(§2(2))。

## 4. アーキテクチャ(確定案: サーバー集約型)

```
[N150サーバー / Dockerコンテナ]
  ├─ 取得系(常駐ワーカー)
  │   ├─ P2P地震情報 WebSocket ×1 (551/552/554/556)
  │   ├─ kmoni EEW JSON 毎秒ポーリング
  │   └─ kmoni 震度画像 毎秒〜2秒毎ポーリング(地震時は1秒固定)
  ├─ 配信系
  │   ├─ 静的ファイル配信(アプリ本体)
  │   ├─ 自前WebSocketサーバー: 地震イベント・新フレーム通知をクライアントへプッシュ
  │   └─ HTTPエンドポイント `/kmoni/latest.gif` 等: サーバーがキャッシュした最新画像を配布
  └─ 死活監視(kmoni疎通断→P2P情報のみの劣化モード)

[リバースプロキシ] https終端。★LAN限定 or 認証必須(§2)

[Pi4 + フルHD] Chromiumキオスクモード
  ├─ 平常時: 震度マップ(毎秒更新) + 時計 + 最新地震情報
  ├─ 地震時: 震央・P/S波円・予想震度・カウントダウン + 音 + 画面明滅
  └─ 設定: EEW通知範囲(予報まで/警報のみ)、音量
```

### 通信境界(重要)

- **クライアント(Pi4等のブラウザ)が通信する相手はこのコンテナのみ**。外部(kmoni/P2P)と通信するのはサーバーだけ。クライアントは (1)コンテナへのWebSocket 1本(イベント受信)、(2)コンテナへのHTTP(静的ファイルと画像取得)だけで完結する。
- **上流P2P WebSocketの扱いは「生プロキシ」ではなく「終端+ファンアウト」**。サーバーがP2Pへ1本だけ接続して受信・パース・正規化し、自前のWSからクライアント全員へ再送する。nginx等でwss://api.p2pquake.netへ素通しプロキシする方式は、全クライアント接続がサーバーIP発になりP2Pの「IPあたり2本」制限に即抵触するため不可。
- kmoni画像の配布は「WSで新フレームのタイムスタンプを通知 → クライアントがHTTPで `/kmoni/latest.gif` を取得」方式を推奨(WSにバイナリを流す方式も可能だが、HTTP配布のほうがキャッシュ制御・デバッグ・実装が単純)。
- kmoniが全てhttpである問題(混在コンテンツ)は、サーバー経由に一本化することで解消。ブラウザから直接kmoniへは行かない。
- クライアント数が増えても外部(NIED/P2P)への負荷は一定。

### リバースプロキシでのwss終端(nginx / AWS ALB 両対応)

- クライアント↔プロキシ間はwss、プロキシ↔コンテナ間は平文ws/httpで問題ない(TLSはプロキシで終端)。
- **nginx**: Upgrade/Connectionはhop-by-hopヘッダでデフォルト転送されないため、`proxy_http_version 1.1;` `proxy_set_header Upgrade $http_upgrade;` `proxy_set_header Connection "upgrade";` を明示。無通信60秒で切断されるため `proxy_read_timeout` を延長(例 3600s)。参考: https://www.getpagespeed.com/server-setup/nginx/nginx-websocket-proxy , https://qiita.com/YuukiMiyoshi/items/d56d99be7fb8f69a751b
- **AWS ALB**: WebSocketをネイティブサポート、特別な設定不要でTLS終端可。ただしアイドルタイムアウトのデフォルトが60秒(最大4000秒に変更可)。参考: https://websocket.org/guides/infrastructure/aws/alb/
- **アプリ側の必須要件(どちらの経路でも共通)**: サーバー→クライアントWSに30秒間隔程度のping/pong(ハートビート)を実装し、クライアントに指数バックオフ付き自動再接続を持たせる。平常時は毎秒フレーム通知が流れるためアイドルになりにくいが、kmoni疎通断の劣化モード中は無通信になりうるので省略不可。
- Pi4は表示専用。フルHDのChromiumキオスクはPi4の能力で十分(参考Aが重いのはScratch VMが原因であり、端末性能の限界ではない)。
- 画面明滅は`requestAnimationFrame`ではなくCSSアニメーション(背景色の点滅)で実装し、音は初回起動時のタップで`<audio>`をアンロックしておく(ブラウザ自動再生制限対策)。Chromiumキオスクなら`--autoplay-policy=no-user-gesture-required`起動フラグでも回避可。

## 5. フロントエンド実装方式の判断基準(React風 vs 軽量構成)

前提の整理: 「参考AのReact版」と「推奨アーキテクチャ」は対立軸ではない。参考Aの重さの原因はScratch VMであってUIフレームワークではなく、**サーバー集約(§4)はどちらのフロントでも共通**。悩むべきは「UI層をReact等で書くか、素のTS+Canvasで書くか」だけ(言語はTypeScriptで確定)。判断の切り口は以下。

1. **毎秒更新の描画パスをフレームワークに通すか** — これが本質。震度マップの毎秒更新をReactのstate/再レンダリングに乗せると無駄が多い。**Canvasを直接操作する描画コアをフレームワーク非依存で書き、Reactは設定画面・タブ・履歴リストなどの「たまにしか変わないUI」だけを担当**する構成なら、Reactでも実行時負荷はほぼ変わらない。
2. **UIの複雑さ** — タブ切替+設定画面+履歴リスト程度なら素のJSでも管理可能な規模。参考A並み(地震/リアルタイム/津波タブ、履歴9件、詳細パネル)まで作り込むなら宣言的UIの恩恵が出る。
3. **保守・ビルドの手間** — 言語は**TypeScriptで確定**(発注者決定。型チェックでビルド時にエラー検出でき、AI開発との相性も良い)。よってビルド工程は前提となり、「ビルドレス」の利点は判断材料から外れる。ビルドはViteまたはesbuildの単純構成とし、Dockerはマルチステージビルド(build stage → 静的ファイルのみ配置)にする。サーバー側もTypeScript(Node.js)で統一し、イベントの型定義をクライアントと共有する。
4. **24時間稼働の安定性** — フレームワークの有無より実装品質(リスナー解除漏れ、画像オブジェクトの解放)が支配的。ただし依存が少ないほどリーク源とアップデート起因の破損は減る。長時間ソークテストを受け入れ条件にすることはどちらでも必須。
5. **Pi4での初期ロード** — Reactバンドル(数百KB)はキオスクで1回読むだけなので実害は小さい。常時表示用途では初期ロードは判断材料としてほぼ無視してよい。

**推奨**: 描画コア(Canvas+WS受信)を**フレームワーク非依存のTypeScriptモジュール**として分離し、UIシェルは (a)規模を絞るなら素のTS、(b)参考A並みの多機能を目指すならPreactかReact(いずれもTS)。どちらを選んでも描画コアは共通なので、後から乗り換え可能な構造にしておくのが実利的。サーバー・クライアント間のWSイベントは共有型定義(monorepoの共通パッケージ or 単一リポジトリの `shared/` ディレクトリ)で管理する。

### 見た目改善(「味気ない」対策)の方向性

- kmoniの配信画像は観測点シンボルの透過オーバーレイなので、**背景地図を自前のダークテーマSVG/PNGに差し替え**、その上にkmoni画像を重ねるだけで印象は大きく変わる(画像の改変ではなく重ね表示に留める)。
- 地震時は予想震度の大型表示・カウントダウン・履歴パネルなどJQuake/参考A風のレイアウトを参考にする。

## 6. 段階的開発プラン(v2)

1. **Phase 1**: サーバー(取得系+SSE配信)+ 震度マップ常時表示 + NIEDクレジット。Dockerイメージ化。
2. **Phase 2**: EEW処理(kmoni JSON+P2P 556)、音+画面明滅、端末別の予報/警報フィルタ設定。
3. **Phase 3**: 津波予報(552)表示・宮崎県沿岸の強調、地震情報履歴、P/S波円・予想震度オーバーレイ。
4. ~~Phase 4: 画像ピクセル→震度値復元~~ → **規約上の理由で除外**(§2(2): 「色から観測値を抽出」する利用は防災科研の意図しない利用と明記されているため)。延岡付近の震度数値は地震後の気象庁発表実測値(P2P 551)で表示する。

### 受け入れ条件に含めるべき項目

- kmoni疎通断時の劣化モード動作(P2P情報のみで継続)
- 72時間ソークテストでメモリ増加なし(サーバー・Pi4双方)
- Pi4フルHDで平常時CPU使用率の実測(目安を仕様化)
- EEWキャンセル報・訓練報の処理(誤報時に明滅を止める)
- 端末時計ズレ時の動作(latest.json基準のオフセット補正)
